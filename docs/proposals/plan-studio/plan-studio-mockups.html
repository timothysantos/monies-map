Recommendation

Build A (Waterfall) as the base, borrow B's pace ring and C's what-if later

  • A answers the owner's question first. "Where does every planned dollar go?" is one bar. Over-allocation is visible without reading a number.
  • It is the only one that lets you manipulate the big picture directly. Dragging a line moves money between jobs. The row sliders handle the granular work. Both feed the same numbers.
  • It degrades cleanly. Simple view keeps today's Earned and Spent bar. The plan bar is simply hidden.
  • It is the cheapest to keep inside the budgets. Plain divs and CSS, no chart library, one lazy chunk.
  • Phase 3 adds C's what-if slider on the savings row, and B's pace marker becomes the "usual by today" tick that A already carries.

Why not B alone: rings are beautiful but make plan editing a two-step trip (tap ring, then sheet). Why not C alone: the chart explains pace well but a month with few days of data looks sparse, and a preview mode adds a state the owner has to learn.

Build notes: what it reuses

  • Data: monthly_plan_rows from the existing month page DTO. Money jobs through splitMoneyUse and money-job-plan. No new fields, no new API.
  • Intent vs Outcome: the header verdict reuses the month lead model (buildMonthLeadModel). The plan-does-not-add-up banner reuses the "Overplanned" idea from "To allocate".
  • Figure menu: the row's three-dot menu is the shared figure-menu with "View entries" and "Ask about this".
  • Month chart: prototype C reuses the Summary column and line chart look and its tooltip rules.
  • Tokens: pastel tokens only. Money tones from money-tone.ts (headroomTone, spendTone). Person colours from person-colour.js. Category colours from category-palette.ts. Job colours are palette picks, not new hues.
  • Saving: same save path as the plan sheet. One db.batch() per "Save plan", with the audit event, and a runBackgroundRefresh afterwards.
  • Mobile: the Month sheet layout query decides phone or desktop. Opening a row for notes, account and date still uses today's plan card.

Build notes: budgets and phases

  • First-screen budget: zero change. The studio is a lazy route chunk (Plan view only), loaded by the warmup scheduler once routeWork.usable is true. No chart library: divs, CSS and a little SVG. Estimated 14 to 18 kB gzip. Simple view loads nothing new.
  • Payload: none. Everything is derived from the month page DTO already sent.
  • Accessibility: every control is a native input or button. Divider lines are role=slider with arrow keys (Shift for 5 steps). 44 px targets. Reduced motion turns every tween into a jump.
  • Phase 1: big-picture header, plan bar, row sliders with typing, nudges, lock, undo, save.
  • Phase 2: pace markers, actual bars, number rolling, flow animation, divider dragging and zoom.
  • Phase 3: what-if slider on the savings target, ring view as an optional second lens.
  • Tests (when built): a failing test per rule below, including the keep-total rule, over-allocation, reset and a failing save keeping the draft.
  • Haptic cues (phones): a light tick on each step crossed while dragging, a soft tap when a slider meets its lock or the keep-total limit, and a double pulse when the plan stops adding up. All optional and off when reduced motion is on.
  • Hidden money: figures become dots, tones go neutral, slices turn grey, sliders keep working, and screen readers hear "amount hidden".

Open questions for the owner

  • Should "Save" show money kept so far (income less spending and investing, as the lead does today) or only what was moved into Savings? The mock uses kept, so it reads far ahead of target early in the month.
  • When you move a slider, should the money default to coming from Left over, or should the plan lock the total? The mock offers both with "Take from".
  • Should changes save as you go, or only on "Save plan"? The mock waits for Save and keeps Undo and Reset to saved.
  • Shared rows: edit the whole row or each person's half? The mock edits the whole row and shows the 50/50 halves as a line.
  • Is a "what if" preview wanted at all? It is the only part that adds a new mode.
  • Pace for bills and rent uses the due date (all due by day 19 count as expected). Is that the pace you want, or a straight line across the month?
